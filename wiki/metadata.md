# Metadata

**Summary**: "Data about data" — the labels, definitions, schemas, owners, operational logs, and lookup codes that make data discoverable, interpretable, and governable. Chapter 2 quotes the DMBOK's **four categories — business, technical, operational, reference** — and argues that metadata becomes a byproduct of well-run data and data processes, turning into a foundation the data engineer can actively consume when designing pipelines.

**Sources**: `raw/fundamentals-of-data-engineering/chapter-02-the-data-engineering-lifecycle.md`

## Why metadata matters

Chapter 2 describes metadata as "exactly the data needed to make data discoverable and governable" — underpinning every section of the [[data-engineering-lifecycle]]. Without metadata, data is unfindable, uninterpretable, and ungovernable (source: raw/fundamentals-of-data-engineering/chapter-02-the-data-engineering-lifecycle.md).

## Autogenerated vs human-generated

Modern data engineering runs on automation, but metadata collection is **often manual and error-prone**. The chapter argues for both: tools can crawl databases for relationships and monitor pipelines to track data flow (autogenerated), while human-oriented systems capture the **social** element — owners, domain experts, context, anecdotes. Airbnb's Dataportal concept is cited as the canonical human-oriented metadata system (source: raw/fundamentals-of-data-engineering/chapter-02-the-data-engineering-lifecycle.md).

Key challenges named: **interoperability and standards remain weak** — metadata tools are only as good as their connectors. And the humans must stay in the loop because data has a social element that pure scanning cannot capture.

Internal wiki/documentation tools provide a foundation for human-oriented metadata, but should integrate with automated catalogs: scanning tools can generate wiki pages with links to relevant data objects (source: raw/fundamentals-of-data-engineering/chapter-02-the-data-engineering-lifecycle.md).

## DMBOK's four categories

Chapter 2 cites the DAMA DMBOK's four categories of metadata useful to data engineers (source: raw/fundamentals-of-data-engineering/chapter-02-the-data-engineering-lifecycle.md):

### 1. Business metadata

How data is used in the business: business and data definitions, data rules and logic, how and where data is used, data owners. Used to answer **nontechnical** "who, what, where, how" questions.

Example from the chapter: a pipeline for "customer sales analysis" needs to know what "customer" means — someone who purchased in the last 90 days? someone who purchased at any time? The data engineer looks this up in a data dictionary or catalog. Business metadata provides the right context and definitions.

### 2. Technical metadata

Describes the data created and used by systems across the lifecycle: **data model, schema, data lineage, field mappings, pipeline workflows**. Common subtypes:

- **Pipeline metadata** — produced by [[orchestration]] systems; captures schedules, system/data dependencies, configurations, connection details.
- **[[data-lineage|Data lineage]]** — tracks origin and changes to data over time; audit trail of evolution through systems.
- **Schema** — structure of data stored in a database, warehouse, lake, or filesystem. A key differentiator across storage systems: object stores don't manage schema (must live in a metastore), while cloud warehouses manage schema internally.

### 3. Operational metadata

Operational results of various systems: process statistics, job IDs, application runtime logs, data used in a process, error logs. Used to determine whether a process succeeded or failed and the data involved.

Current state: orchestration systems provide a limited picture; operational metadata remains "scattered across many systems." Better operational metadata is a major motivator for **next-generation orchestration and metadata-management systems** (source: raw/fundamentals-of-data-engineering/chapter-02-the-data-engineering-lifecycle.md).

### 4. Reference metadata

Data used to classify other data — also called **lookup data**. Examples: internal codes, geographic codes, units of measurement, internal calendar standards. A standard for interpreting other data. Changes slowly over time by nature (source: raw/fundamentals-of-data-engineering/chapter-02-the-data-engineering-lifecycle.md).

## Metadata as a foundation

Once metadata systems and processes exist, the data engineer can consume metadata in useful ways — it becomes a foundation for designing pipelines and managing data across the lifecycle, not just documentation generated after the fact (source: raw/fundamentals-of-data-engineering/chapter-02-the-data-engineering-lifecycle.md).
